# Agent maintenance and validation

This is the in-repository successor to the lab guidance formerly stored in a project-specific Hermes skill. Read `../remit.md` first.

## Lab-bench maintenance workflow
Use this for runnable-lab maintenance in `/workspace/growing-neural-networks`. Keep `labs/` focused on pure-Python code, tiny datasets, algorithm traces, static browser demos, tests, and validators; do not mix bulk literature-review/PDF work into a lab change.

1. Start with `git status --short` in `/workspace/growing-neural-networks`; stop if uncommitted user work exists.
2. Read `README.md`, `docs/remit.md`, `docs/roadmap.md`, `data/experiments.json`, and `data/lab-algorithms.json` before selecting work.
3. Choose exactly one small improvement, prioritizing an existing available lab's runnable code, tests, validation, README, static demo, or concise cross-links back to the main garden. Add a new pure-Python mechanism only when the roadmap clearly calls for it.
4. Keep dependencies light and static-site friendly: no torch/tensorflow/numpy unless the repo explicitly adopts them later.
5. Validate with `python3 scripts/validate_lab.py`, every test path listed for available experiments in `data/experiments.json`, `node --check` for changed JavaScript when node is available, `python3 -m json.tool` for changed JSON, `git diff --check`, and an HTTP smoke test of changed/static HTML or data routes via `python3 -m http.server` on an available local port. If improving the lab validator itself, it is safe to execute each available pure-Python lab script with `sys.executable`, `cwd` set to the script directory, a short timeout, and JSON parsing of stdout so stale script paths/non-JSON regressions are caught without adding dependencies. When a lab publishes a static trace artifact such as `trace.json`, strengthen the validator to compare that snapshot exactly with the runnable script output; this keeps static-site data honest without adding dependencies. Prefer validating trace snapshots through the lab-local `experiment.json` `artifacts` map rather than hardcoding `trace.json`: require artifact paths to be relative, lab-local (no absolute paths or `..`), and present on disk, then compare a declared `trace` artifact against the script output. Generate such snapshots by running the lab script directly and redirecting stdout to the JSON file, then check it with `python3 -m json.tool`. For browser demos that display the trace, prefer loading the canonical `trace.json` with static `fetch()` over duplicating rounded constants in JavaScript; this prevents the HTML demo, committed snapshot, and Python script from drifting apart while remaining static-site friendly. If the first port is busy, retry with a dynamically chosen port; a reliable pattern is to launch a tiny Python `ThreadingHTTPServer` that binds `('127.0.0.1', 0)`, smoke-tests URLs with `urllib.request`, and shuts down in `finally`. Do not start `python3 -m http.server 0` as a background process and expect to recover the selected port from logs; in this environment the port may not be visible promptly, so the inline `ThreadingHTTPServer` smoke-test script is more deterministic. Avoid piping generated JSON directly into another Python interpreter (for example `python script.py | python3 -m json.tool`) because security guards may treat pipe-to-interpreter as executable-content risk; instead run the script directly for output, or write/read a temporary JSON file when a JSON syntax pass is actually needed.
6. Commit locally with `lab: improve <thing>` or `lab: add <thing>`; never push.
7. Final report: changed artifact, validations, commit hash, and blockers if any.
